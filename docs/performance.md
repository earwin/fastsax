# fastsax performance

Measured results and the methodology behind them. Architecture background is
in [design.md](design.md); approaches that were measured and rejected are in
[negative-results.md](negative-results.md). All numbers are from real runs
and are not restated when the code changes — treat them as provenance, not a
contract; re-run the benchmarks on your own hardware and inputs.

## Methodology

- **Hardware**: an Apple M1 Pro (10 cores, darwin/arm64) and an AMD Ryzen 7
  5800H (Zen 3, Windows, real AVX2). Go 1.25 on both. Rosetta 2 was used
  only for amd64 *correctness* runs (it does not translate AVX2, and its
  performance is not representative — no amd64 perf numbers were ever taken
  under it).
- **End-to-end A/B comparisons**: two separately built test binaries,
  interleaved runs alternating order (ABBA), 5–12 rounds, medians. Thermal
  drift on the M1 Pro machine is ±5%, so single same-process comparisons
  were not trusted for cross-build deltas; at least one measurement that
  showed an implausibly favorable delta (+27% where the dedicated run said
  +15%) was traced to drift and discarded.
- **Isolated (component) benchmarks**: same-binary sub-benchmarks over the
  full corpus, with windows carved exactly like the sequential parser and
  record spans carved exactly like stage-1 groups, so the measured loop is
  byte-for-byte the production shape. Parity of every variant against the
  stock scanner is asserted on the whole corpus before any timing.
- **Utilization**: cross-checked with rusage ((user+sys)/wall busy cores),
  not sampling profiles, when claiming a change moved throughput rather than
  scheduling.
- Same-process back-to-back ratios (e.g. the stage-1 grid below) are
  meaningful as *ratios*; their absolute numbers depend on machine load.

## Corpora

Generated by `cmd/genxml` (deterministic, seeded — byte-identical across
platforms for the same flags):

| corpus | recipe | shape |
|---|---|---|
| default | `go run ./cmd/genxml -size 100MB -out testdata/out.xml` | ~193k records ~540B each, 2 attrs/record, 2% CDATA fields, 1% comments, ~9.8 input bytes/event |
| clean | `-cdata 0 -comments 0` (benchmarks: set `FASTSAX_CLEAN_XML`) | construct-free variant of default |
| attrheavy | `-attrs 8 -attrvaluelen 20-60` | 114,880 records ~915B, ~25% of attr values contain a raw `>`, ~25% an apostrophe; start-tag bytes ≈ 45% of scan time |
| attrdense | `-attrs 12 -fieldattrs 4 -fields 4` | 65,082 records ~1.6KB, records are nearly all start-tag bytes |

The default corpus is the same workload gosax's baseline benchmark uses, so
gosax numbers are directly comparable. The benchmark workload is gosax's
`BenchmarkReader_Event` workload: for every `<location>` field, substring
search in its text. Benchmarks skip with instructions when
`testdata/out.xml` is absent; `FASTSAX_BENCH_XML` points them at an existing
corpus.

## Parallel stage 1: sequential vs parallel boundary scan

The parallel plateau used to be the sequential stage-1 skeleton.
Back-to-back same-process comparison, stage 1 forced sequential vs forced
parallel (`BenchmarkParallelStage1`, MB/s, M1 Pro; this grid predates the
SIMD hit mask — it still illustrates the seq-vs-par split accurately):

| corpus | stage1 | w=1 | w=2 | w=4 | w=8 |
|---|---|---|---|---|---|
| default | seq | 619 | 1727 | 1738 | 1664 |
| default | par | 619 | 1694 | 3248 | 4234 |
| clean | seq | 633 | 1765 | 1840 | 1803 |
| clean | par | 625 | 1766 | 3285 | 4453 |

Sequential stage 1 caps the whole pipeline at ~1.7–1.8 GB/s no matter the
worker count; parallel stage 1 (activated at `Workers >= 4`) lifts that cap,
and with the SIMD hit mask the pipeline reaches 4.75 GB/s (default) /
5.1 GB/s (clean) at 8 workers.

## SIMD hit-mask kernels

Component rates for `maskByte64` (one `'<'` movemask word per 64 input
bytes, whole-window pass):

| kernel | hardware | GB/s |
|---|---|---|
| NEON (CMEQ + 3×ADDP fold) | M1 Pro | ~51 |
| AVX2 (2× VPCMPEQB/VPMOVMSKB) | Ryzen 7 5800H | 70.7 |
| SSE2 (4× PCMPEQB/PMOVMSKB) | Ryzen 7 5800H | 42.8 |
| pure-Go SWAR | Ryzen 7 5800H | 4.9 |
| pure-Go SWAR | M1 Pro | ~3.5 |

Candidate search in `findHit` (isolated, full corpus, build cost included):
the previous serial 8-byte SWAR sweep ran at 2.69 GB/s; the mask-driven bit
iterator runs at 6.19 GB/s — **2.3x**.

End-to-end effect of landing the two scanner changes (the per-window mask
kernel in stage 1 and the 16-byte SWAR text probe in the scanners) against
the immediately preceding tree, interleaved A/B, separately built binaries,
5 alternating rounds, medians, M1 Pro:

| bench | before | after | delta |
|---|---|---|---|
| SequentialMem/prefetch | 977 MB/s | 1044 MB/s | **+6.9%** |
| SequentialMem/noprefetch | 966 MB/s | 1027 MB/s | **+6.3%** |
| ParseRecords mem/trivial w4 | 3160 MB/s | 3468 MB/s | **+9.8%** |
| ParseRecords mem/trivial w8 | 4325 MB/s | 5108 MB/s | **+18.1%** |
| ParseRecords mem/heavy w4 | 2003 MB/s | 2093 MB/s | +4.5% |
| ParseRecords mem/heavy w8 | 2985 MB/s | 3360 MB/s | **+12.6%** |
| ParallelClean w8 | 4573 MB/s | 5166 MB/s | **+13.0%** |

The trivial-w8 row is from a dedicated w8-only A/B with rusage capture:
busy cores 8.2 → 8.5. A mixed-set measurement of the same pair showed
+26.1%, inflated by favorable thermal drift — the dedicated number is the
honest one. The two wins compose almost additively (+5.4% and +14.2%
measured singly ≈ +18.5% together at w8) because they live in disjoint
loops: the text probe in the stage-2/sequential scanners, the mask in
stage-1 candidate search.

An independent repeat A/B (ABBA, 6 rounds, same machine under heavier
desktop load — absolute numbers lower, deltas consistent): SequentialMem
prefetch 965→1023 (+6.0%), noprefetch 952→991 (+4.1%); ParseRecords
mem/trivial w4 3242→3477 (+7.3%), w8 4165→4785 (+14.9%); mem/heavy w8
2989→3308 (+10.7%); ParallelClean w8 4386→4750 (+8.3%); an ad-hoc Ordered
w8 bench 2743→2795 (+1.9% — ordered delivery serializes the handler, so
stage-2 gains barely show; no regression). rusage at trivial w8: ~8.0 busy
cores for both binaries — same utilization, higher throughput.

Allocation profile: the mask buffers add a few allocations (~660KB) to the
per-`ParseRecords`-call setup constant; 0 allocs per record is unchanged.

## Tape names

The scanner records start-tag name lengths in the tape essentially for free
(the name loop's several compares became one table load — interleaved A/B
measured 0% scanner cost). A consumer that switches from `Name(b.Bytes(e))`
to `b.Name(e)` gains ~10% end-to-end on the name-heavy benchmark workload
(`BenchmarkSequentialMemTapeName` vs `BenchmarkSequentialMem`). End-tag name
lengths are deliberately *not* recorded (~2% scanner cost for names
consumers rarely need). In record mode the predictor caches the name length
per learned token; the residual cost on `ParseRecords` workers=1 measured
~1.5%, invisible at ≥2 workers.

## Reading the numbers honestly

- **Input-dependent.** The fast walker consumes `"<!"`/`"<?"` constructs
  per construct, so sparse CDATA/comments (the default corpus's 2% CDATA
  fields) do not knock whole windows back to the full walker — the
  default-vs-clean gap at 8 workers is ~5%. Only truly hostile shapes
  (record-tag text inside quoted attributes, quotes throughout
  record-adjacent content) disable the fast path, degrading toward the
  stage1=seq row above, never below it.
- **Attribute-heavy shapes are not a weakness.** They parse *faster* per
  byte than the default corpus (quoted values are bulk-skipped by
  `IndexByte`; bytes/event is higher): attrheavy sequential 1318 MB/s,
  w4 4644, w8 4388; attrdense sequential 2265, w4 3110, w8 3381 (M1 Pro,
  same-process). Attempts to speed them up further with extra masks all
  measured negative — see negative-results.md.
- **Activation thresholds**: the parallel stage-1 pre-walk engages at
  `Workers >= 4`; below that, stage 1 runs sequentially and throughput tops
  out around 1.6–1.8 GB/s. With pre-walking active, scaling continues to
  8–10 workers, where stage-2 workers become the ceiling again.
- **Heavy handlers** (FNV-hash every name and payload) cost what they
  compute — and keep scaling with workers (425 → 3084 MB/s from 1 to 8
  workers). When sequential stage 1 was the ceiling they looked free; its
  plateau hid the handler cost.
- **Allocations**: sequential parsing is 0 allocs/op steady-state and
  `ParseRecords` is 0 allocs per record; each `ParseRecords` *call* pays a
  setup constant (~60–230 allocs, growing with worker count). Both are
  enforced by tests.
- File vs in-memory input barely differs on a page-cached file; prefetch
  matters more for genuinely slow readers. On slow inputs (network)
  everything is I/O-bound; `RecordStats.IOBound()` reports it so callers
  can drop `Workers` for subsequent runs.
